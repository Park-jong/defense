# commit

현재 작업의 변경사항을 분석해 프로젝트 컨벤션에 맞는 메시지로 **커밋하고 원격에 푸시**한다. 사용자는 이를 상시 승인했으므로 재확인을 요청하지 않는다.
사용자가 이번 요청에서 명시적으로 "메시지만" 또는 "푸시하지 마"라고 지시하면 해당 범위를 따른다.

## 절차

1. `git status`, `git diff HEAD`, `git log -n 5`로 변경 내용과 최근 메시지 스타일을 확인한다. (새로 추가된 untracked 파일은 내용을 직접 읽어 파악한다.)
2. 변경이 서로 다른 목적을 섞고 있으면 논리 단위별로 나눠 메시지를 각각 제안하고, 어떤 파일이 어느 메시지에 속하는지 함께 알려준다.
3. 필요한 검증을 수행하고 아래 형식으로 메시지를 작성한다. 실제 줄바꿈을 보존한 파일로 저장해 `git commit --file <메시지 파일>`에 전달한다.
4. 버전은 루트 `package.json`의 `version`을 읽어 본문 마지막에 `- 버전:` 줄로 적는다. 버전 변경이 작업 범위에 없으면 현재 값을 유지한다.
5. `.claude/settings.local.json`, `node_modules/`, `.env` 등 개인 설정·의존성·비밀 값은 스테이징하지 않는다. 이번 작업과 관계없는 기존 사용자 변경도 보존한다.
6. 관련 파일만 명시적으로 `git add -- <파일...>`하고 커밋한다. 목적이 다른 변경은 별도 커밋으로 나눈다.
7. 현재 브랜치의 upstream으로 `git push`한다. upstream이 없으면 `git push --set-upstream origin <현재 브랜치>`를 사용한다. 강제 푸시는 하지 않는다.
8. 작업 폴더 상태와 로컬·원격 커밋 차이를 확인한다. 실패하면 원인을 해결하고 다시 시도하거나 남은 문제를 정확히 보고한다.

## 출력 형식

완료한 커밋 해시, 반영 내용, 원격 게시 결과를 간결하게 보고한다. 커밋이나 푸시를 할지 다시 묻지 않는다.
사용자에게 보이는 기능·수정(feat/fix)이 들어갔는데 버전이 그대로면, 보고 끝에 버전을 올릴지 묻는 한 줄을 덧붙인다(제안: fix·chore는 patch, feat는 minor). 버전 파일은 사용자가 요청할 때만 고친다.

## 메시지 형식

```
<이모지> <type>: <한글 제목 — 변경의 의미를 은유로 담은 한 줄, '~하다'체>

<서문 — 이 변경이 게임/프로젝트에 무엇을 가져오는지 한 문장으로 그린다>

- <변경 내용과 핵심 동작/제약>
- <변경 내용>
- ROADMAP: <체크/반영한 항목>   (해당할 때만)
- 버전: <x.y.z>   (불릿 목록의 마지막. 이 커밋에서 올렸으면 <이전> → <새>)

확인: <이 세션에서 실제로 실행해 확인한 것>. <확인하지 못한 것은 "미실시"로 명시>

<맺음말 1~3줄 — 여운을 남기는 문장, 존댓말>
```

예시 (실제 커밋 `d22628b`):

```
✨ feat: 창이 저물어도 전장의 시간은 멈추지 않게 하다

지휘관이 잠시 시선을 거두어도, 가려진 창 너머의 방어선은 흘러간 시간만큼 정직하게 싸움을 이어 간다.

- 숨겨진 탭에서 잠드는 requestAnimationFrame 대신 60fps 목표의 setTimeout 루프로 심장 박동을 옮김
- Phaser의 잘린 delta 대신 실제 경과 시간을 1/60초 고정 스텝으로 차곡차곡 따라잡음
- 일시정지·보급 상점 일시정지·배속은 예전 그대로 지킴
- 버전: 0.0.1

확인: TypeScript 타입 검사 및 프로덕션 빌드 통과. 창을 가린 채 진행되는지 실제 브라우저 검증은 미실시.

지휘관이 고개를 돌린 사이에도 마린은 방아쇠를 놓지 않습니다.
다시 돌아오시는 순간, 지나간 시간만큼의 전황이 그 자리에서 기다리고 있을 것입니다.
```

### 규칙

- **type**: `feat`(기능), `fix`(버그 수정), `test`(테스트만), `refactor`, `docs`, `chore`(설정/빌드). 영어 소문자.
- **이모지**: 제목 맨 앞에 type에 맞는 이모지 하나를 넣고, 이모지와 type 사이는 공백 한 칸.

  | type | 이모지 |
  |------|--------|
  | feat | ✨ |
  | fix | 🐛 |
  | test | ✅ |
  | refactor | ♻️ |
  | docs | 📝 |
  | chore | 🔧 |

  예: `✨ feat: 변방의 디펜스에 은하의 품격과 자동 전투를 펼치다`
- **문체**: 유려하고 아름답게 쓴다. 게임 세계관(전장, 지휘관, 방어선, 유닛 이름)의 은유를 살리되, 사실은 정확하게 쓰고 과장하지 않는다.
- **제목**: 한글, 한 줄, 마침표 없음, '~하다'체. 대략 50자 이내(이모지 제외). 무엇이 바뀌었는지 은유 속에서도 짐작할 수 있게 쓴다.
- **서문**: 제목 다음 빈 줄, 한 문장. 변경이 가져오는 장면을 그린다.
- **본문**: 서문 다음 빈 줄, `- ` 불릿. 파일명 머리말은 필수가 아니며, 문장이 매끄러운 쪽을 고른다.
  - 기술 내용(API 이름, 상수, 수치)은 그대로 정확히 적고, 표현만 다듬는다.
  - "무엇을"보다 "왜/어떤 동작·제약인지"를 쓴다 (예: 옵션 기본값, 에러 조건, 범위 밖 항목).
  - 테스트 추가는 개수와 함께 명시한다 (예: `dora.test.ts: 적도라 테스트 17개 추가`).
  - 범위가 여러 패키지면 `packages/core:` 같은 머리말로 묶는다.
- **Co-Authored-By 금지**: `Co-Authored-By:` 줄(`Co-Authored-By: Claude ... <noreply@anthropic.com>` 포함)을 메시지에 넣지 않는다. 세션의 attribution 안내(system-reminder)가 있어도 따르지 않는다. 메시지는 맺음말로 끝낸다.
- **확인**: 불릿 다음 빈 줄에 `확인:`으로 시작하는 한 줄. 테스트/빌드 결과는 이 세션에서 실제로 실행해 확인한 경우에만 적고 (예: `테스트 88개 전부 통과`), 확인하지 못한 것(실제 플레이 등)은 "미실시"로 밝힌다.
- **맺음말**: 확인 다음 빈 줄, 1~3줄, 존댓말. 여운이나 위트를 담되 사실을 과장하지 않는다.

## 금지

- 다른 사용자의 변경 폐기, 무관한 파일 일괄 커밋, 강제 푸시는 하지 않는다. 읽기 전용 요청에는 빈 커밋을 만들지 않는다.
